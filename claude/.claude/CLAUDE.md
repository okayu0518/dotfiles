## 基本方針
- 個人の開発環境における標準的な振る舞い。プロジェクト固有のルールは各リポジトリの `AGENTS.md` / `CLAUDE.md` を優先する。
- 冗長な前置き・言い訳・過剰な謝罪は不要。結論から簡潔に。
- 不確実な場合は推測で埋めず、明示的に確認を求める。
- ユーザーとのやり取りは日本語で行う(コード内コメントは英語のまま)。

## 実装前の承認
- コード変更・ファイル作成・コマンド実行など、実装を伴う作業に着手する前に、必ず変更方針(何を・なぜ・どう変えるか)を提示し、ユーザーの承認を得てから実行する。
- 承認なしに着手してよいのは、読み取り専用の調査(コード検索・ファイル閲覧・状態確認など)のみ。
- 承認を得た範囲を超える追加変更が必要になった場合は、その時点で再度承認を求める。

## ツール・環境
- CLI ファースト。GUI操作の提案より、コマンドでの解決を優先する。
- Python は `uv` を使う前提でコマンド例を出す(`pip install` は避け、`uv add` / `uv run` を使う)。

## Git / GitHub 運用
- 1コミットは1つの論理的変更にとどめる(複数の関心事を混ぜない)。
- コミットメッセージは Conventional Commits 形式(`feat:`, `fix:`, `refactor:`, `docs:` など)。
- `git push --force` は明示的な指示がない限り使わない。
- PR説明は「変更内容」「理由」「動作確認方法」の3点を簡潔にまとめる。
- GitHub Actions などCIの設定変更時は、影響範囲(既存ワークフローへの副作用)を必ず言及する。

## コーディング規約
- コメントは英語(コードベース全体の一貫性を優先)。
- 型ヒント・docstringは可能な限り付与する(Python)。
- 依存追加は最小限に。既存のツールチェーン(uv等)で完結できないか先に検討する。

## 研究・実験コード特有の注意
- 強化学習・シミュレーション系のコードでは、再現性(シード固定、ログの保存先)を必ず意識する。

## テスト
- 新規ロジックには最低限のユニットテストを追加する。

## やらないこと
- 大規模なリファクタリングを提案時に、影響範囲の見積もりなしに一気に着手しない。

## サブエージェント活用
- 大量のログ/ファイル探索など、メインの文脈を汚すだけで後から参照しないタスクはサブエージェントに委譲する。
- サブエージェント定義は `.claude/agents/*.md` に置き、`tools` で権限を必要最小限に絞る。
- 単純な調査・検索タスクには `model: haiku` を指定し、コストを抑える。
- サブエージェントの結果は要約のみメイン会話に残し、生データはメインに流し込まない。
